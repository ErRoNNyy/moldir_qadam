HEALTHY FOOD PLANNER APP — PRODUCT IDEA & WORKFLOW
=====================================================

1. PRODUCT OVERVIEW
-------------------

The app is a cross-platform mobile + desktop/web application for people who
follow a healthy lifestyle and want an easier way to discover, organize,
cook, plan, and track high-protein / lower-calorie meals.

The main problem:

People discover recipes on YouTube, but when they actually want to cook them,
they have to:
- find the video again;
- search through the video;
- pause and rewind;
- write down ingredients;
- understand quantities;
- estimate calories and macros;
- remember what they planned to eat;
- manually create shopping lists;
- remember what they actually ate.

The app should turn this into one continuous workflow:

YouTube → paste link → AI structures recipe → save → put on calendar
→ generate shopping list → cook → mark as eaten → track history

The key product idea is NOT simply "AI recipe extraction".

The stronger product is:

A PERSONAL FOOD PLANNER + RECIPE DATABASE + NUTRITION TRACKER +
CALENDAR + SHOPPING LIST.

The AI is the entry point that makes the workflow easy.


2. MAIN APP SECTIONS
--------------------

The primary navigation should have four main sections:

1. VIDEO
2. CALENDAR
3. SHOPPING
4. YOU / PROFILE

Recommended interpretation of each section:

VIDEO
------
The input and recipe-import section.

Purpose:
- Paste a YouTube video link.
- Analyze the video.
- Extract the recipe.
- Show structured ingredients.
- Show cooking instructions.
- Estimate nutrition.
- Allow the user to edit the result.
- Save the recipe.

CALENDAR
--------
The planning section.

Purpose:
- Plan meals for specific days.
- Assign meals to breakfast/lunch/dinner or other meal types.
- View daily and weekly plans.
- See calories and macros for planned meals.
- Mark planned meals as eaten.
- Move or reschedule meals.

SHOPPING
--------
The execution section.

Purpose:
- Automatically generate a shopping list from planned meals.
- Combine repeated ingredients across recipes.
- Group ingredients into logical categories.
- Let users check ingredients off while shopping.
- Allow manual additions/removals.

YOU / PROFILE
-------------
The personal history and statistics section.

Purpose:
- Track what the user actually ate.
- View nutrition history.
- View recent meals.
- See favorite/most-cooked recipes.
- See statistics and trends.
- Reuse meals from previous days/weeks.


3. CORE PRODUCT LOOP
--------------------

The main loop of the application is:

1. User finds a recipe on YouTube.
2. User opens the app.
3. User pastes the YouTube link.
4. Backend obtains available video information/transcript and/or other
   accessible content.
5. AI analyzes the content.
6. AI converts the recipe into structured data.
7. The app displays:
   - recipe title;
   - ingredients;
   - quantities;
   - servings;
   - preparation/cooking steps;
   - estimated calories;
   - protein;
   - carbohydrates;
   - fat.
8. User reviews and edits the extracted information.
9. User saves the recipe.
10. User adds the recipe to a calendar date.
11. The calendar becomes the user's weekly meal plan.
12. The app generates a shopping list from planned meals.
13. User shops using the list.
14. User cooks the planned meal.
15. User marks the meal as "Eaten".
16. The meal is added to food history.
17. Nutrition totals are updated.
18. The user can later look at previous meals and reuse them.

6. IMPORTANT AI / NUTRITION RULE
--------------------------------

Nutrition should NOT rely entirely on the LLM guessing calories.

The preferred pipeline is:

Video / transcript
   ↓
LLM extracts ingredients + quantities
   ↓
Normalize ingredients
   ↓
Match ingredients to a nutrition database
   ↓
Calculate calories/macros from ingredient quantities
   ↓
Aggregate totals
   ↓
Display estimated nutrition
   ↓
Allow user editing

Reason:

A video can say:
- "add some olive oil"
- "take some chicken"
- "a little cheese"
- "one handful of nuts"

These quantities are ambiguous.

Therefore the application should show nutrition as ESTIMATED and let users
correct ingredient quantities.

The user should be able to edit:
- quantity;
- unit;
- serving size;
- ingredient;
- nutrition values where necessary.

20. PRODUCT PHILOSOPHY
----------------------

The app should optimize for LOW FRICTION.

Users should not have to manually enter everything.

Bad workflow:

Search food
→ select ingredient
→ enter amount
→ enter calories
→ enter protein
→ confirm
→ repeat

Better workflow:

Paste recipe
→ AI creates everything
→ user quickly checks it
→ add to calendar
→ cook
→ one tap "Eaten"

The goal is:

ONE-TAP / LOW-EFFORT TRACKING.


21. KEY PRODUCT RISK
--------------------

The biggest product risk is not technically extracting recipes.

It is user retention.

Many people say:
"I want to track my food."

Then stop doing it after a few days because tracking becomes annoying.

Therefore:
- importing recipes must be fast;
- adding meals to the calendar must be easy;
- marking meals as eaten must be one action;
- shopping lists must be automatic;
- historical meals must be easy to reuse.

The application should reduce work rather than create another tracking chore.


22. KEY TECHNICAL RISK
----------------------

AI extraction from videos can be inaccurate.

Potential problems:
- ingredients only visible on screen;
- incomplete transcripts;
- vague quantities;
- missing measurements;
- spoken instructions that differ from visible ingredients;
- ambiguous serving sizes;
- oil/sauce amounts not specified.

Solution:
- present extracted data as editable;
- use AI for extraction, not as the only nutrition source;
- use a nutrition database for calculated values;
- clearly label values as estimates when appropriate.
